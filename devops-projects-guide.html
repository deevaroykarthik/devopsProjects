Where to start

  • Strongest networking story: 1, then 3, then 8. Together they show segmentation, hybrid connectivity, and everything as code.

Before you start any project

  • Create an AWS account, enable MFA on the root user, and set up an AWS Budgets alert before launching anything. Work with an IAM Identity Center or IAM user, not root.
  • Install Git, Terraform 1.10 or newer, the AWS CLI v2, Docker, and Python 3.12. Individual projects list extra tools.
  • Replace placeholders such as ap-south-1, bucket names, and YOUR_USER/YOUR_REPO with your own values.
  • Treat every environment as disposable. Destroy resources after each session, since NAT gateways, load balancers, VPNs, and Kubernetes clusters bill by the hour.
  • Never commit secrets, keys, or account IDs. Use OIDC and GitHub secrets, and check the Git history before you publish a repository.

A production-style AWS network, built with Terraform and CI/CD

Build a multi-tier network on AWS, define it entirely as code, and let a GitHub Actions pipeline plan, apply, and deploy a containerized app into it. This is the foundation the later projects build on.

Level
Beginner to intermediate
Time
2 to 3 weekends, part-time
Skills practiced
AWS networking, Terraform, Docker, GitHub Actions, CloudWatch
Cost
Low if you destroy it after each session. NAT gateways and load balancers bill by the hour.

Architecture

Public traffic enters through an internet gateway and an Application Load Balancer. The app runs in private subnets across two availability zones, and a pipeline in GitHub builds and deploys everything.

  • Public subnet
  • Private app subnet
  • Private data subnet
  • Request path
  • Outbound internet through NAT

How a request travels

  1. A user hits the load balancer's DNS name. Traffic enters the VPC through the internet gateway.
  2. The load balancer, placed in the public subnets, forwards requests to healthy tasks in the private subnets. Security groups allow the app port only from the load balancer.
  3. Tasks have no public IPs. When they need the internet (OS updates, external APIs), their route table sends 0.0.0.0/0 to the NAT gateway in the public subnet.
  4. Fargate pulls the container image from ECR. Flow logs record accepted and rejected traffic for troubleshooting.

Before you start

  • An AWS account with a budget alert set (AWS Budgets) and MFA on the root user. Do the work with an IAM Identity Center or IAM user, not root.
  • Installed locally: Terraform 1.10 or newer, AWS CLI v2, Docker, and Git.
  • A GitHub account and an empty repository for the project.
  • Basic comfort with CIDR notation and routing. If you work in networking, you already have the hardest part of this project covered.

Replace ap-south-1, bucket names, and YOUR_USER/YOUR_REPO in the snippets with your own values.

Build steps

  1. Set up the repository layout

    Separate the application, the reusable Terraform modules, and the environment that wires them together. This structure is easy to extend with a second environment later.

    layout
    devops-aws-project/
├── app/                      # sample app + Dockerfile
├── infra/
│   ├── bootstrap/            # one-time: remote state bucket
│   ├── modules/
│   │   ├── network/          # VPC, subnets, routes, NAT
│   │   └── service/          # ALB, ECS, security groups
│   └── envs/
│       └── dev/              # calls the modules
└── .github/workflows/        # pipelines

  2. Create the remote state bucket

    Terraform needs a safe, shared place to keep its state. Create the bucket once from infra/bootstrap using local state, then point every other configuration at it.

    infra/bootstrap/main.tf
    resource "aws_s3_bucket" "state" {
  bucket = "YOUR-UNIQUE-NAME-tfstate"
}

resource "aws_s3_bucket_versioning" "state" {
  bucket = aws_s3_bucket.state.id
  versioning_configuration {
    status = "Enabled"
  }
}

resource "aws_s3_bucket_public_access_block" "state" {
  bucket                  = aws_s3_bucket.state.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}
    infra/envs/dev/backend.tf
    terraform {
  backend "s3" {
    bucket       = "YOUR-UNIQUE-NAME-tfstate"
    key          = "dev/terraform.tfstate"
    region       = "ap-south-1"
    use_lockfile = true   # S3-native locking (Terraform 1.10+)
  }
}

    On older Terraform versions, use a DynamoDB table for locking with the dynamodb_table argument instead of use_lockfile.

  3. Write the network module

    Create the VPC, two public subnets, two private app subnets, an internet gateway, and route tables. Use cidrsubnet() so the addressing plan stays readable.

    infra/modules/network/main.tf
    data "aws_availability_zones" "available" {
  state = "available"
}

resource "aws_vpc" "main" {
  cidr_block           = "10.0.0.0/16"
  enable_dns_hostnames = true
  tags = { Name = "${var.project}-vpc" }
}

resource "aws_subnet" "public" {
  count                   = 2
  vpc_id                  = aws_vpc.main.id
  cidr_block              = cidrsubnet(aws_vpc.main.cidr_block, 8, count.index)
  availability_zone       = data.aws_availability_zones.available.names[count.index]
  map_public_ip_on_launch = true
  tags = { Name = "${var.project}-public-${count.index}" }
}

resource "aws_subnet" "private_app" {
  count             = 2
  vpc_id            = aws_vpc.main.id
  cidr_block        = cidrsubnet(aws_vpc.main.cidr_block, 8, count.index + 10)
  availability_zone = data.aws_availability_zones.available.names[count.index]
  tags = { Name = "${var.project}-private-app-${count.index}" }
}

resource "aws_internet_gateway" "igw" {
  vpc_id = aws_vpc.main.id
}

resource "aws_route_table" "public" {
  vpc_id = aws_vpc.main.id
  route {
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.igw.id
  }
}

resource "aws_route_table_association" "public" {
  count          = 2
  subnet_id      = aws_subnet.public[count.index].id
  route_table_id = aws_route_table.public.id
}

  4. Add NAT and private routing

    Private subnets need a default route to a NAT gateway for outbound access. The diagram shows one per availability zone, which is the resilient setup. For a low-cost lab, start with one NAT gateway shared by both zones and note the trade-off in your README.

    infra/modules/network/nat.tf
    resource "aws_eip" "nat" {
  domain = "vpc"
}

resource "aws_nat_gateway" "nat" {
  allocation_id = aws_eip.nat.id
  subnet_id     = aws_subnet.public[0].id
  depends_on    = [aws_internet_gateway.igw]
}

resource "aws_route_table" "private" {
  vpc_id = aws_vpc.main.id
  route {
    cidr_block     = "0.0.0.0/0"
    nat_gateway_id = aws_nat_gateway.nat.id
  }
}

resource "aws_route_table_association" "private_app" {
  count          = 2
  subnet_id      = aws_subnet.private_app[count.index].id
  route_table_id = aws_route_table.private.id
}

  5. Create the security groups, load balancer, and service

    In modules/service, define two security groups and chain them: the load balancer accepts web traffic from the internet, and the app accepts traffic only from the load balancer's security group. Then add an ALB, a target group, an ECS cluster, a task definition, and an ECS service on Fargate in the private subnets.

    infra/modules/service/security.tf
    resource "aws_security_group" "alb" {
  name   = "${var.project}-alb"
  vpc_id = var.vpc_id

  ingress {
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }
  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}

resource "aws_security_group" "app" {
  name   = "${var.project}-app"
  vpc_id = var.vpc_id

  ingress {
    from_port       = 8080
    to_port         = 8080
    protocol        = "tcp"
    security_groups = [aws_security_group.alb.id]
  }
  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}

    Set assign_public_ip = false on the ECS service's network configuration so tasks stay private. Start with HTTP on port 80; add HTTPS with ACM and Route 53 as an extension.

  6. Containerize a small app

    Any small web app with a /health endpoint works. Point the target group's health check at it.

    app/Dockerfile
    FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 8080
CMD ["gunicorn", "-b", "0.0.0.0:8080", "app:app"]

    Create an ECR repository in Terraform and push a first image manually so the ECS service has something to run before the pipeline takes over.

  7. Give GitHub Actions access without long-lived keys

    Use OpenID Connect so the pipeline requests short-lived credentials. In IAM, add an identity provider for token.actions.githubusercontent.com, then create a role with this trust policy. Grant the role only the permissions the pipeline needs, not administrator access, and store its ARN as the repository secret AWS_ROLE_ARN.

    trust-policy.json
    {
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "Federated": "arn:aws:iam::ACCOUNT_ID:oidc-provider/token.actions.githubusercontent.com"
    },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "token.actions.githubusercontent.com:aud": "sts.amazonaws.com"
      },
      "StringLike": {
        "token.actions.githubusercontent.com:sub": "repo:YOUR_USER/YOUR_REPO:*"
      }
    }
  }]
}

  8. Build the infrastructure pipeline

    On pull requests the workflow checks formatting, validates, and plans. On merge to main it applies the saved plan. Add a required reviewer through a GitHub Environment if you want a manual approval before apply.

    .github/workflows/infra.yml
    name: infra
on:
  pull_request:
    paths: ["infra/**"]
  push:
    branches: [main]
    paths: ["infra/**"]

permissions:
  id-token: write
  contents: read

jobs:
  terraform:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: infra/envs/dev
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_ROLE_ARN }}
          aws-region: ap-south-1
      - uses: hashicorp/setup-terraform@v3
      - run: terraform fmt -check -recursive
      - run: terraform init
      - run: terraform validate
      - run: terraform plan -out=tfplan
      - if: github.event_name == 'push' && github.ref == 'refs/heads/main'
        run: terraform apply -auto-approve tfplan

  9. Build the application pipeline

    On every change under app/, build the image, push it to ECR, and tell ECS to roll out a new deployment. This version pushes both a commit-SHA tag and latest and has the task definition use latest, which keeps the first version simple. Using the SHA tag in the task definition is a good upgrade later.

    .github/workflows/app.yml
    name: app
on:
  push:
    branches: [main]
    paths: ["app/**"]

permissions:
  id-token: write
  contents: read

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_ROLE_ARN }}
          aws-region: ap-south-1
      - id: ecr
        uses: aws-actions/amazon-ecr-login@v2
      - name: Build and push
        run: |
          REPO=${{ steps.ecr.outputs.registry }}/devops-demo
          docker build -t $REPO:${{ github.sha }} -t $REPO:latest app/
          docker push $REPO --all-tags
      - name: Roll out
        run: |
          aws ecs update-service \
            --cluster devops-demo \
            --service devops-demo \
            --force-new-deployment

  10. Add observability

    Turn on VPC Flow Logs so you can see accepted and rejected traffic, and add CloudWatch alarms for the load balancer's 5xx count and unhealthy host count, notifying an SNS topic. You also need a log group and an IAM role that lets flow logs write to it.

    infra/modules/network/flowlogs.tf
    resource "aws_cloudwatch_log_group" "flow" {
  name              = "/vpc/${var.project}/flow-logs"
  retention_in_days = 7
}

resource "aws_flow_log" "vpc" {
  vpc_id          = aws_vpc.main.id
  traffic_type    = "ALL"
  log_destination = aws_cloudwatch_log_group.flow.arn
  iam_role_arn    = aws_iam_role.flow.arn   # role trusted by vpc-flow-logs.amazonaws.com
}

Verify it works

  • Opening the load balancer's DNS name in a browser returns your app's response.
  • Running a second terraform plan shows no changes. The code and the real infrastructure agree.
  • The ECS tasks have no public IP, and you cannot reach port 8080 on them directly from the internet.
  • From a task, outbound requests succeed. Temporarily removing the private default route makes them fail, and restoring it fixes them.
  • Pushing a change under app/ produces a new image in ECR and a new ECS deployment without any manual steps.
  • A pull request that breaks formatting (terraform fmt) fails the pipeline.
  • In CloudWatch Logs Insights, you can find rejected connections in the flow logs, for example by filtering on action = "REJECT".

Clean up and cost

NAT gateways and load balancers charge for every hour they exist, even with no traffic. Treat the environment as disposable.

  • Run terraform destroy in infra/envs/dev at the end of each session, and recreate it from the pipeline next time. That doubles as a good test of your code.
  • Delete images in ECR and, last of all, the state bucket in bootstrap.
  • Keep the AWS Budgets alert active and check the Billing console after your first week.

Stretch goals

  • Add HTTPS: request a certificate in ACM, add an HTTPS listener, redirect HTTP, and manage DNS in Route 53.
  • Create a second environment (envs/prod) that reuses the same modules, with an approval step between dev and prod.
  • Add tflint and a scanner such as Checkov to the pull request workflow so insecure infrastructure fails before merge.
  • Replace Fargate with Kubernetes (Project 4).

Next project: 2. Config backup and compliance

Network config backup and compliance checker

Automatically pull running configs from network devices, keep every version, and flag any device that drifts from your baseline. This is the closest project to a networking job, so it is the easiest to explain in an interview.

Level
Beginner
Time
1 to 2 weekends
Skills practiced
Python, Netmiko, YAML, boto3, S3, GitHub Actions
Cost
Near zero. The lab runs locally and S3 storage is a few cents.

Architecture

A scheduled workflow connects to each device, saves its config to a versioned S3 bucket, and compares it with rules kept in Git. Any violation raises an alert.

How it works

  1. A scheduled GitHub Actions workflow starts the backup job.
  2. The job connects to each device over SSH with Netmiko and runs the platform's show running-config command.
  3. Each config is uploaded to a versioned S3 bucket, so every change is kept as a version.
  4. The compliance checker compares the latest config to the required and forbidden lines in baseline.yaml.
  5. If any device breaks a rule, the run fails and posts an alert to Slack.

Build steps

  1. Prepare devices to test against

    You need devices reachable over SSH. Good options: the Cisco DevNet always-on sandbox, a containerlab or EVE-NG or GNS3 lab, or spare lab gear. Create a read-only user for the backup job.

    If the devices sit on a private network, GitHub-hosted runners cannot reach them. Use a self-hosted runner inside that network, or test against a publicly reachable sandbox.

  2. Describe your inventory in YAML

    inventory.yaml
    devices:
  - name: edge-r1
    host: 192.0.2.11
    device_type: cisco_xe
  - name: edge-r2
    host: 192.0.2.12
    device_type: cisco_ios

    Keep credentials out of this file. The script reads them from environment variables.

  3. Write the backup script

    backup.py
    import os

import boto3
import yaml
from netmiko import ConnectHandler

BUCKET = os.environ["CONFIG_BUCKET"]
s3 = boto3.client("s3")


def fetch_config(device):
    conn = ConnectHandler(
        device_type=device["device_type"],
        host=device["host"],
        username=os.environ["NET_USER"],
        password=os.environ["NET_PASS"],
    )
    config = conn.send_command("show running-config")
    conn.disconnect()
    return config


def main():
    with open("inventory.yaml") as f:
        devices = yaml.safe_load(f)["devices"]
    for d in devices:
        try:
            config = fetch_config(d)
        except Exception as exc:
            print(f"FAILED {d['name']}: {exc}")
            continue
        # Same key every run: S3 versioning keeps the history.
        s3.put_object(
            Bucket=BUCKET,
            Key=f"configs/{d['name']}/running-config.txt",
            Body=config.encode(),
        )
        print(f"saved {d['name']}")


if __name__ == "__main__":
    main()

  5. Define the baseline and the checker

    List lines that must be present and lines that must never appear. Start with three or four rules you would actually enforce.

    baseline.yaml
    required:
  - "service password-encryption"
  - "ntp server 192.0.2.50"
  - "logging host 192.0.2.60"
forbidden:
  - "transport input telnet"
  - "ip http server"
    compliance.py
    import os

import boto3
import yaml

s3 = boto3.client("s3")
BUCKET = os.environ["CONFIG_BUCKET"]


def config_lines(device):
    obj = s3.get_object(Bucket=BUCKET, Key=f"configs/{device}/running-config.txt")
    return {line.strip() for line in obj["Body"].read().decode().splitlines()}


def check(device, baseline):
    cfg = config_lines(device)
    problems = [f"missing: {r}" for r in baseline["required"] if r not in cfg]
    problems += [f"forbidden: {r}" for r in baseline["forbidden"] if r in cfg]
    return problems


if __name__ == "__main__":
    baseline = yaml.safe_load(open("baseline.yaml"))
    inventory = yaml.safe_load(open("inventory.yaml"))["devices"]
    failed = False
    for d in inventory:
        problems = check(d["name"], baseline)
        if problems:
            failed = True
            print(f"{d['name']}: " + "; ".join(problems))
    raise SystemExit(1 if failed else 0)

    This is exact-line matching, which is deliberately simple. Indentation is ignored and no ip http server does not match ip http server.

  6. Schedule it and alert on failure

    Create the AWS role for GitHub with OIDC as in Project 1, step 7, then add the workflow. A failed compliance run triggers the Slack message.

    .github/workflows/config-backup.yml
    name: config-backup
on:
  schedule:
    - cron: "0 */6 * * *"
  workflow_dispatch:

permissions:
  id-token: write
  contents: read

jobs:
  backup-and-check:
    runs-on: ubuntu-latest   # use a self-hosted runner for private devices
    env:
      CONFIG_BUCKET: YOUR-UNIQUE-NAME-net-configs
      NET_USER: ${{ secrets.NET_USER }}
      NET_PASS: ${{ secrets.NET_PASS }}
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_ROLE_ARN }}
          aws-region: ap-south-1
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install netmiko boto3 pyyaml
      - run: python backup.py
      - run: python compliance.py
      - name: Alert on drift
        if: failure()
        env:
          SLACK_WEBHOOK: ${{ secrets.SLACK_WEBHOOK }}
        run: |
          curl -X POST -H 'Content-type: application/json' \
            --data '{"text":"Config compliance check failed. Open the workflow run for details."}' \
            "$SLACK_WEBHOOK"

Verify it works

  • Running the workflow manually creates one object per device in S3.
  • Changing a device (for example, enabling telnet) makes the next run fail and posts a Slack alert.
  • Reverting the change makes the next run pass, and the bucket's version list shows both versions of that config.
  • No passwords or webhook URLs appear anywhere in the repository.

Clean up and cost

Empty the bucket (including all versions) before destroying it, and disable the scheduled workflow when you are not using it.

Stretch goals

  • Run the backups in parallel with Nornir instead of a plain loop.
  • Include a diff of the latest and previous versions in the alert, using difflib.
  • Commit configs to a Git repository instead of S3 and open a pull request when something changes.
  • Render the intended config from Jinja2 templates and compare it with the real one (this leads into Project 6).

Next project: 3. Transit Gateway hub-and-spoke

Hub-and-spoke network with Transit Gateway

Connect several VPCs and a simulated on-premises site through one Transit Gateway, and control exactly who can talk to whom with separate route tables. This is network segmentation, expressed as Terraform.

Level
Intermediate
Time
2 weekends
Skills practiced
Transit Gateway, route tables, IPsec VPN, Terraform modules
Cost
Moderate. Transit Gateway attachments and VPN connections bill by the hour, so destroy after each session.

Architecture

Spoke VPCs attach to a central Transit Gateway. Separate TGW route tables make spokes reach shared services and on-premises, but never each other.

How it works

  1. Each VPC attaches to the Transit Gateway through subnets you choose.
  2. An association decides which TGW route table an attachment uses for its outgoing traffic. A propagation decides whose routes appear in a table.
  3. The spokes table learns routes only from shared services and the VPN, so spoke A has no route to spoke B and that traffic is dropped.
  4. The shared table learns all VPCs, so shared services and on-premises can reach every spoke.

Build steps

  1. Plan non-overlapping address space

    Write the plan before any code. Overlapping CIDRs are the most common reason hub-and-spoke builds fail.

    NetworkCIDRRole
    Shared services10.0.0.0/16DNS, tooling, bastion
    Spoke A10.1.0.0/16Workload
    Spoke B10.2.0.0/16Workload
    Simulated on-prem10.100.0.0/16Stands in for a data center

  2. Reuse the network module from Project 1

    Change the module so the VPC CIDR is a variable (cidr_block = var.cidr), and make it output vpc_id, private_subnet_ids, and the private route table ID. Then create four VPCs.

    infra/envs/hub/vpcs.tf

  source  = "../../modules/network"
  project = "shared"
  cidr    = "10.0.0.0/16"
}

module "spoke_a" {
  source  = "../../modules/network"
  project = "spoke-a"
  cidr    = "10.1.0.0/16"
}

module "spoke_b" {
  source  = "../../modules/network"
  project = "spoke-b"
  cidr    = "10.2.0.0/16"
}

module "onprem" {
  source  = "../../modules/network"
  project = "onprem"
  cidr    = "10.100.0.0/16"
}

  3. Create the Transit Gateway without default route tables

Next project: 4. Kubernetes networking on EKS

Kubernetes networking on EKS

Run a two-tier app on EKS, expose it through an Application Load Balancer created from a Kubernetes Ingress, manage DNS automatically, and lock down pod-to-pod traffic with network policies.

Level
Intermediate
Time
2 to 3 weekends
Skills practiced
EKS, Helm, Ingress, ExternalDNS, Kubernetes NetworkPolicy
Cost
Moderate. The EKS control plane, nodes, and load balancer all bill hourly.

Architecture

A controller inside the cluster creates the load balancer and DNS records from Kubernetes objects. Network policies then limit which pods may talk to each other.

How it works

  1. A user resolves the app hostname in Route 53 and reaches the ALB.
  2. The AWS Load Balancer Controller created that ALB from your Ingress, and it sends traffic straight to pod IPs.
  3. ExternalDNS watches the Ingress and writes the Route 53 record for you.
  4. A default-deny NetworkPolicy blocks all pod traffic, and explicit policies allow only ALB to frontend and frontend to api.

Build steps

  1. Create the cluster with eksctl

    This config enables the OIDC provider (needed for IAM roles for service accounts) and turns on network policy support in the VPC CNI add-on.

    cluster.yaml
    apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig
metadata:
  name: demo
  region: ap-south-1
iam:
  withOIDC: true
addons:
  - name: vpc-cni
    configurationValues: '{"enableNetworkPolicy": "true"}'
managedNodeGroups:
  - name: ng-1
    instanceType: t3.medium
    desiredCapacity: 2
    minSize: 2
    maxSize: 3
    terminal
    eksctl create cluster -f cluster.yaml
kubectl get nodes

    Cluster creation takes about 15 minutes. You can later move this to Terraform with the community EKS module.

  2. Install the AWS Load Balancer Controller

    Create its IAM policy and service account, then install the Helm chart. Check the controller's documentation for the current policy file, since it changes between versions.

    terminal
    curl -o iam_policy.json https://raw.githubusercontent.com/kubernetes-sigs/aws-load-balancer-controller/main/docs/install/iam_policy.json

aws iam create-policy \
  --policy-name AWSLoadBalancerControllerIAMPolicy \
  --policy-document file://iam_policy.json

eksctl create iamserviceaccount \
  --cluster demo --namespace kube-system \
  --name aws-load-balancer-controller \
  --attach-policy-arn arn:aws:iam::ACCOUNT_ID:policy/AWSLoadBalancerControllerIAMPolicy \
  --approve

helm repo add eks https://aws.github.io/eks-charts
helm repo update
helm install aws-load-balancer-controller eks/aws-load-balancer-controller \
  -n kube-system \
  --set clusterName=demo \
  --set serviceAccount.create=false \
  --set serviceAccount.name=aws-load-balancer-controller

    If you use your own VPC instead of the one eksctl creates, tag public subnets with kubernetes.io/role/elb=1 and private subnets with kubernetes.io/role/internal-elb=1.

  3. Deploy a two-tier app

    Start from deny-all, then allow only the flows you intend. The ALB sends traffic from addresses inside your VPC, so the frontend policy allows your VPC CIDR.

Next project: 5. Network monitoring and alerts

Network monitoring and alerting

Turn VPC Flow Logs and service metrics into alarms, dashboards, and answers. You will detect spikes in rejected traffic, watch NAT and load balancer health, and investigate with queries.

Level
Intermediate
Time
1 to 2 weekends
Skills practiced
VPC Flow Logs, CloudWatch, SNS, Logs Insights, Grafana
Cost
Low. Keep log retention short and delete the stack afterward.

Architecture

Flow logs feed two paths: CloudWatch Logs for alarms and quick queries, and S3 for cheap long-term storage. Service metrics go to Grafana.

How it works

  1. Flow logs from the VPC land in a CloudWatch log group and in an S3 bucket.
  2. A metric filter counts REJECT records. A CloudWatch alarm fires when the count spikes and notifies an SNS topic.
  3. SNS delivers the alert by email, or to Slack through a chat integration.
  4. CloudWatch metrics for NAT gateways, load balancers, and VPN are charted in Grafana.
  5. Optionally, query the archived flow logs in S3 with Athena.

Build steps

  1. Send flow logs to CloudWatch and S3

    Setting a 60-second aggregation interval gives you faster feedback while testing. The CloudWatch destination also needs an IAM role that the flow logs service can assume.

    flowlogs.tf
    resource "aws_cloudwatch_log_group" "flow" {
  name              = "/vpc/demo/flow-logs"
  retention_in_days = 7
}

resource "aws_flow_log" "to_cloudwatch" {
  vpc_id                   = var.vpc_id
  traffic_type             = "ALL"
  max_aggregation_interval = 60
  log_destination          = aws_cloudwatch_log_group.flow.arn
  iam_role_arn             = aws_iam_role.flow.arn   # trusted by vpc-flow-logs.amazonaws.com
}

resource "aws_flow_log" "to_s3" {
  vpc_id               = var.vpc_id
  traffic_type         = "ALL"
  log_destination_type = "s3"
  log_destination      = aws_s3_bucket.flow_archive.arn
}

  2. Alert on rejected traffic

    A metric filter turns matching log lines into a metric, and an alarm watches it.

    alerts.tf
    resource "aws_sns_topic" "alerts" {
  name = "network-alerts"
}

resource "aws_sns_topic_subscription" "email" {
  topic_arn = aws_sns_topic.alerts.arn
  protocol  = "email"
  endpoint  = var.alert_email
}

resource "aws_cloudwatch_log_metric_filter" "rejects" {
  name           = "rejected-traffic"
  log_group_name = aws_cloudwatch_log_group.flow.name
  pattern        = "[version, account, eni, source, destination, srcport, destport, protocol, packets, bytes, windowstart, windowend, action=\"REJECT\", flowlogstatus]"

  metric_transformation {
    name      = "RejectedFlows"
    namespace = "Network"
    value     = "1"
  }
}

resource "aws_cloudwatch_metric_alarm" "reject_spike" {
  alarm_name          = "rejected-traffic-spike"
  namespace           = "Network"
  metric_name         = "RejectedFlows"
  statistic           = "Sum"
  period              = 300
  evaluation_periods  = 1
  threshold           = 500
  comparison_operator = "GreaterThanThreshold"
  treat_missing_data  = "notBreaching"
  alarm_actions       = [aws_sns_topic.alerts.arn]
}

    Confirm the subscription from the email AWS sends, or the alarm has nowhere to go.

Next project: 6. NetDevOps pipeline

NetDevOps: network changes through a pipeline

Treat network configuration like application code. Intent lives in Git, a pull request renders and validates the configs, and merging deploys them and runs post-checks.

Level
Advanced
Time
3 to 4 weekends
Skills practiced
Ansible, Jinja2, Batfish, pytest, GitHub Actions, Git workflows
Cost
Free if you use a local lab and a self-hosted runner.

Architecture

Engineers edit YAML intent files. CI renders configs and checks them with Batfish before anything touches a device. Only merged changes are deployed.

How it works

  1. An engineer changes a YAML file (for example, adds an interface or a BGP neighbor) and opens a pull request.
  2. CI lints the YAML, renders device configs from Jinja2 templates, and runs Batfish checks for undefined references and duplicate IPs.
  3. After review, the merge to main starts the deployment job.
  4. Ansible pushes the rendered configuration to the lab devices.
  5. Post-deploy tests check that routing actually works. If they fail, revert the merge and the pipeline restores the previous state.

Build steps

  1. Set up the repository

    layout
    netdevops/
├── host_vars/              # per-device intent (YAML)
├── templates/              # Jinja2 config templates
├── inventory.yml           # Ansible inventory
├── deploy.yml              # Ansible playbook
├── render.py               # builds configs from intent
├── tests/
│   ├── batfish/            # pre-deploy checks
│   └── post_checks/        # post-deploy checks
└── .github/workflows/

  2. Describe intent and write the template

    Keep data and syntax separate. The YAML says what you want, and the template knows how the platform expresses it.

    host_vars/r1.yml
    hostname: r1
interfaces:
  - name: Loopback0
    ip: 10.255.0.1
    mask: 255.255.255.255
  - name: GigabitEthernet1
    ip: 10.0.12.1
    mask: 255.255.255.252
bgp:
  asn: 65001
  neighbors:
    - ip: 10.0.12.2
      remote_as: 65002
    templates/ios.j2
    hostname {{ hostname }}
{% for i in interfaces %}
interface {{ i.name }}
 ip address {{ i.ip }} {{ i.mask }}
 no shutdown
{% endfor %}
router bgp {{ bgp.asn }}
{% for n in bgp.neighbors %}
 neighbor {{ n.ip }} remote-as {{ n.remote_as }}
{% endfor %}

  3. Render the configs

    Batfish reads a snapshot folder with a configs directory, so render straight into that layout.

    render.py
    import pathlib

import yaml
from jinja2 import Environment, FileSystemLoader

env = Environment(loader=FileSystemLoader("templates"), trim_blocks=True, lstrip_blocks=True)
out = pathlib.Path("build/snapshot/configs")
out.mkdir(parents=True, exist_ok=True)

for path in pathlib.Path("host_vars").glob("*.yml"):
    data = yaml.safe_load(path.read_text())
    config = env.get_template("ios.j2").render(**data)
    (out / f"{data['hostname']}.cfg").write_text(config)
    print(f"rendered {data['hostname']}")

  4. Validate before deploying with Batfish

    Batfish analyzes the configs offline, so mistakes are caught before any device sees them. Start the Batfish container locally, then run the test.

    terminal
    docker run -d --name batfish -p 9996:9996 batfish/allinone
pip install pybatfish pytest
    tests/batfish/test_snapshot.py
    from pybatfish.client.session import Session


def test_network_is_consistent():
    bf = Session(host="localhost")
    bf.set_network("lab")
    bf.init_snapshot("build/snapshot", name="candidate", overwrite=True)

    undefined = bf.q.undefinedReferences().answer().frame()
    assert undefined.empty, f"Undefined references:\n{undefined}"

    duplicates = bf.q.ipOwners(duplicatesOnly=True).answer().frame()
    assert duplicates.empty, f"Duplicate IPs:\n{duplicates}"

Next project: 7. Self-healing infrastructure

Self-healing infrastructure

Detect an unhealthy instance and fix it automatically: first try a cheap repair, and if that fails, replace the instance. Every action is reported to the on-call team.

Level
Advanced
Time
2 weekends
Skills practiced
Auto Scaling, CloudWatch, EventBridge, Lambda, Systems Manager, IAM
Cost
Low. Two small instances, a load balancer, and a few Lambda runs.

Architecture

A CloudWatch alarm on unhealthy hosts triggers a Lambda through EventBridge. The Lambda restarts the service with Systems Manager, waits, and tells the Auto Scaling group to replace any instance that is still failing.

How it works

  1. The load balancer health check marks an instance unhealthy and the UnHealthyHostCount alarm goes into ALARM.
  2. EventBridge receives the alarm state change and invokes the remediation Lambda.
  3. Step 1: the Lambda uses SSM Run Command to restart the service on the unhealthy instances.
  4. Step 2: after a wait, any instance that is still unhealthy is marked unhealthy in the Auto Scaling group, which launches a replacement.
  5. The Lambda publishes each action to an SNS topic so a human can see what happened.

Build steps

  1. Build the base: an Auto Scaling group behind a load balancer

    Reuse the VPC, subnets, and ALB from Project 1. Instances sit in private subnets and need NAT (or VPC endpoints) to install packages and reach Systems Manager. Attach an instance profile with the AmazonSSMManagedInstanceCore policy.

  2. Alarm on unhealthy hosts

  3. Write the remediation Lambda

    The function tries the cheap fix first, waits, and escalates only for instances that are still unhealthy.

    heal.py
    import os
import time

import boto3

elbv2 = boto3.client("elbv2")
ssm = boto3.client("ssm")
asg = boto3.client("autoscaling")
sns = boto3.client("sns")

TG_ARN = os.environ["TARGET_GROUP_ARN"]
TOPIC_ARN = os.environ["TOPIC_ARN"]


def unhealthy_instances():
    health = elbv2.describe_target_health(TargetGroupArn=TG_ARN)["TargetHealthDescriptions"]
    return [t["Target"]["Id"] for t in health if t["TargetHealth"]["State"] == "unhealthy"]


def notify(message):
    sns.publish(TopicArn=TOPIC_ARN, Subject="Self-healing action", Message=message)


def handler(event, context):
    bad = unhealthy_instances()
    if not bad:
        return {"handled": []}

    # Step 1: try the cheap fix
    ssm.send_command(
        InstanceIds=bad,
        DocumentName="AWS-RunShellScript",
        Parameters={"commands": ["systemctl restart nginx"]},
    )
    notify(f"Restarted nginx on {bad}")

    # Step 2: wait, then replace anything still unhealthy
    time.sleep(90)
    still_bad = [i for i in unhealthy_instances() if i in bad]
    for instance_id in still_bad:
        asg.set_instance_health(
            InstanceId=instance_id,
            HealthStatus="Unhealthy",
            ShouldRespectGracePeriod=False,
        )
    if still_bad:
        notify(f"Restart did not help. ASG is replacing {still_bad}")
    return {"handled": bad, "replaced": still_bad}

Next project: 8. Hybrid cloud VPN lab

Hybrid cloud connectivity lab

Connect a simulated on-premises network to an AWS VPC over IPsec with BGP, then test failover between the two tunnels. This is the project where a networking background pays off most.

Level
Advanced
Time
2 to 3 weekends
Skills practiced
Site-to-Site VPN, IPsec, BGP, strongSwan, FRR, Terraform, Ansible
Cost
Low to moderate. The VPN connection bills by the hour, so destroy it after each session.

Architecture

A Linux router running strongSwan and FRR stands in for your data center. It builds two IPsec tunnels to AWS and exchanges routes with BGP.

How it works

  1. The on-prem router establishes two IPsec tunnels to the AWS VPN endpoints.
  2. Inside each tunnel, BGP advertises your on-prem LAN to AWS and AWS advertises the VPC CIDR back.
  3. The virtual private gateway propagates the learned routes into the VPC route table, so instances know how to reach on-prem.
  4. If one tunnel fails, BGP withdraws its routes and traffic continues over the other tunnel.

Build steps

  1. Plan addresses and ASNs

    ItemValue
    On-prem LAN192.168.10.0/24
    AWS VPC10.0.0.0/16
    On-prem ASN65010
    AWS side ASN64512
    Tunnel inside addressesAssigned by AWS from 169.254.0.0/16

  2. Choose how to build the on-prem side

    You need a Linux machine with a reachable public IP. Two practical options:

    • A lab on your own machine (EVE-NG, GNS3, or containerlab) with a router VM. If it is behind a home NAT, set the customer gateway IP to your public address and forward UDP 500 and 4500. AWS supports NAT traversal.
    • A small EC2 instance in another VPC or region acting as the router. This is the quickest and most repeatable option.

  3. Create the AWS side with Terraform

    vpn.tf
    resource "aws_vpn_gateway" "vgw" {
  vpc_id          = module.vpc.vpc_id
  amazon_side_asn = 64512
}

resource "aws_customer_gateway" "onprem" {
  bgp_asn    = 65010
  ip_address = var.onprem_public_ip
  type       = "ipsec.1"
}

resource "aws_vpn_connection" "onprem" {
  vpn_gateway_id      = aws_vpn_gateway.vgw.id
  customer_gateway_id = aws_customer_gateway.onprem.id
  type                = "ipsec.1"
  static_routes_only  = false   # use BGP
}

resource "aws_vpn_gateway_route_propagation" "private" {
  vpn_gateway_id = aws_vpn_gateway.vgw.id
  route_table_id = module.vpc.private_route_table_id
}

output "tunnel1_address" {
  value = aws_vpn_connection.onprem.tunnel1_address
}

    Allow ICMP and SSH from 192.168.10.0/24 on the test instance's security group.

  4. Download the VPN configuration

    In the VPC console, open the VPN connection and choose Download configuration. Pick Strongswan if it is listed, otherwise Generic. The file contains the tunnel endpoints, IKE and IPsec parameters, pre-shared keys, and the inside tunnel addresses you need next.

  5. Prepare the on-prem router

    terminal

    Apply the IPsec parameters and secrets from the downloaded file to strongSwan, create the tunnel interfaces it describes, and start the tunnels. Then configure BGP with the inside addresses from the same file:

    /etc/frr/frr.conf (excerpt)

 neighbor 169.254.11.1 remote-as 64512     ! tunnel 2 AWS inside address
 !

  network 192.168.10.0/24
 exit-address-family

    The inside addresses above are placeholders. Use the ones in your downloaded configuration.

  6. Verify the tunnels and BGP

    terminal

sudo ipsec statusall

  --vpn-connection-ids vpn-0123456789abcdef0 \

  7. Test connectivity and failover

    Ping the EC2 test instance's private address from a host on the on-prem LAN while you break one tunnel. Watch BGP and the ping.

    Once it works by hand, capture the strongSwan and FRR configuration as Ansible templates so you can rebuild the on-prem side in minutes.

Verify it works

  • Both tunnels show UP in the VPN connection telemetry, and BGP shows Established for both neighbors.
  • The VPC route table contains 192.168.10.0/24 learned through the virtual private gateway.
  • The on-prem host reaches the EC2 instance by private IP, and the instance can reach the on-prem host.
  • Taking down one tunnel causes a short interruption at most, then pings continue over the second tunnel.
